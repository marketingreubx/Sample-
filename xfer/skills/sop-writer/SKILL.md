# SOP Writer

An SOP is good when someone new can follow it without asking questions and get the same quality result. That means exact steps, the expected result after each step, the decisions they will face, and the mistakes to avoid.

## What to collect

1. The task and why it matters.
2. How the user does it now (a voice note transcript, notes, a Loom summary, or a walkthrough).
3. Who will follow it and their skill level.
4. Tools, logins and files involved.
5. What "done well" looks like.

## The structure

1. **Title and purpose:** what this process achieves.
2. **When to use:** trigger and frequency.
3. **Owner and roles.**
4. **Before you start:** tools, access, files, time needed.
5. **Steps:** numbered, one action per step, starting with a verb. After each: "You should now see..." For complex steps, sub-steps. Placeholders for screenshots or video timestamps.
6. **Decision points:** "If X, do Y. If not, go to step 8."
7. **Quality checklist:** what to check before marking done.
8. **Common mistakes and fixes.**
9. **Hand off:** who to notify, where to save, what to update.
10. **Time estimate.**
11. **Version and last updated.**

## Rules

- Write for the least experienced person who will use it.
- One action per step.
- Exact names of buttons, menus, files and folders.
- No sensitive passwords in the document; refer to the password manager.
- Test by mentally following each step.

## Output format

```
SOP: [Title]
Purpose ... | When ... | Owner ... | Time ...

BEFORE YOU START
- [ ] ...

STEPS
1. ... → You should see ...
   [Screenshot]
2. ...

DECISIONS
...

QUALITY CHECK
- [ ] ...

COMMON MISTAKES
...

WHEN DONE
...

Version 1.0, updated [date]
```

## Final check

- [ ] A beginner could follow it
- [ ] Expected result after key steps
- [ ] Decision points covered
- [ ] Quality checklist included
